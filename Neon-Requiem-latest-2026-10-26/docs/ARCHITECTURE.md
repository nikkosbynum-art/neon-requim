# Architecture

**Status: Prototype architecture implemented in part; full game architecture remains planned.**

## Runtime flow

- `scenes/main.tscn` is a minimal launch scene.
- `scripts/main.gd` creates the UI and actor nodes, forwards presentation snapshots to actors, and passes wave changes to `scripts/environment/environment_director.gd`. The director selects a data-driven zone and crossfades outgoing/incoming instances of `scripts/environment/undercity_backdrop.gd`; it has no combat authority. `data/zones/undercity_prototype_zones.json` contains two palette-only Undercity test modules. The wave-13 boundary is a reversible QA fixture, not approved content pacing or a canonical location division.
- `scripts/combat/combat_director.gd` owns encounter state, six-slot ally movement/attacks, nearest-living-ally enemy targeting, attack timing, damage, defeat, and wave transitions. It emits `combat_action_resolved` after applying each attack, with a monotonic sequence, source/target IDs, side, style, damage, and post-hit HP. Subscribers receive a deep copy for presentation; no signature-ability events are implemented yet. It advances using a fixed simulation step. The default `direct_damage` mode preserves the existing deterministic control. An opt-in `hybrid_trial` mode (`--neon-hybrid-trial`) uses the configurable, explicitly provisional profile at `data/combat/hybrid_combat_trial.json`: living-unit current/max HP, attack power, and cadence form each side's power score; every committed attack samples a bounded high-impact likelihood from relative side power and a seeded encounter RNG. Actions resolve before the maximum/no-progress timers; either timer can trigger the approved defeat/retreat flow. Hybrid validation is pending Test Lane and no trial value is canon. Each entity's data-driven combat style and engagement distance control its approach: ranged entities hold configured stand-off distances and melee entities close to contact. After a victory, allies carry remaining HP into the next wave, and any ally at 0 HP remains defeated. After full-squad defeat, the squad retreats to the highest cleared holding wave and restores to full HP before retrying. This supersedes the earlier same-day full-heal-at-each-wave rule. Current HP is run state and is stored per slot. The Undercity grunt's 1.6 per-wave damage increase remains a configurable prototype value, not a canon balance curve.
- `data/squads/undercity_six_slot.json` defines the six active prototype slots. Slot one references BREAKER; the other five use clearly marked generic placeholder names, stats, internal movement speeds, combat styles, and staggered depth positions until canonical recruit data is verified and individual character implementation is in scope. Slots 2–3 provisionally exercise ranged stand-off; slots 4–6 provisionally exercise melee contact. These defaults do not implement player-defined preferences.
- `scripts/progression/economy.gd` owns prototype run credits, deterministic upgrade costs/purchases, recruit run-levels, and run save data. It does not implement permanent progression.
- The BREAKER x1/x10 HUD path prepares its candidate run state, saves it through `SaveService`, then applies the matching level, credit, HP, and Influence-adjusted attack-power changes to the live combat director. The 1.12 growth value is a playtest candidate; no level cap is defined.
- `scripts/main.gd` handles the authoritative `wave_cleared` event by building candidate permanent rewards and a complete run snapshot, adding an offline timestamp, then committing all sections through `SaveService`. If disk persistence fails, the completed encounter and rewards remain in memory and the HUD asks for manual Save; the atomic save service keeps the previous file intact.
- `scripts/progression/offline_earnings_service.gd` calculates a claim from the persisted run's highest-cleared holding wave, using the shared ordinary encounter reward calculator and a configurable hourly rate/cap. On load, `scripts/main.gd` persists the candidate permanent/run/settings payload through `SaveService` before applying credits in memory. The operation changes no wave state and runs no encounters. The current one-reward-per-hour rate is a user-approved feasibility trial, not final balance; legacy saves without a claim timestamp start from a saved baseline without retroactive credits.
- `scripts/progression/research_service.gd` provides a pure rank purchase transaction and a save-before-apply wrapper for permanent Network Influence. The UI lists the four approved research branches from `data/progression/research_catalog.json`; node arrays are intentionally empty until costs, prerequisites, and effects receive approved values. The prototype does not apply research gameplay effects.
- `scripts/characters/breaker_t1_placeholder_rig.gd` builds a temporary `Skeleton2D`/`Bone2D` hierarchy with independently attached polygon parts for BREAKER Tier I. It covers the specified identity anchors and visualizes supplied animation state; it is not a sprite rig made from approved artwork. `docs/BREAKER_RIG_CONTRACT.md` records the tested simulation/presentation boundary and effect marker API that an eventual art replacement must preserve.
- `scripts/presentation/placeholder_actor.gd` is the generic stand-in for enemies and the five unassigned allies; it visualizes supplied position, depth, health, and animation state. It does not decide outcomes.
- `scripts/presentation/attachment_event_router.gd` routes simulation-owned structured events to registered presentation receivers by owner actor instance/source or owner actor instance/target. It passes each receiver a deep copy, rejects duplicate/out-of-order event sequence numbers, and has no combat API. It is connected to `scripts/main.gd` and headless-tested end-to-end; no character-specific equipment node is registered in the runtime scene.
- `CombatDirector.snapshot()` remains authoritative for gameplay and saves. `presentation_snapshot()` interpolates actor positions between fixed steps for display only; it never changes combat positions or persisted values.
- `data/` contains configurable JSON definitions for BREAKER, generic squad slots, one basic enemy, and Undercity wave rules.
- `scripts/persistence/save_service.gd` reads and writes a versioned JSON save under Godot's `user://` path. It verifies staged, backup, committed, and restored payloads semantically, retains `.bak`/`.bak.prev` recovery sidecars during replacement, and validates fallback data before load. The version 1 schema has no migration path yet.

## Intended growth areas

Keep future combat simulation independent from visuals, use data resources for characters/enemies/waves, separate permanent progression from current-run progression and settings, and keep the UI scalable. The six active slots and automatic combat are represented, but player-defined formation preferences, individual definitions for five allies, abilities/Redline, the complete economy, research node data/effects, cyberware, production sprite parts, and a completed reusable production rig remain unimplemented. System Reboot, the generic all-recruit evolution transaction, capped offline credit claims, wave-clear autosaves, and the read-only research framework are integrated for prototype feasibility; final offline rate, research nodes, tier stat/trait effects, and evolution art are not.

## Provisional technical assumptions

**Provisional:** scalable `canvas_items` interface with future touch support, JSON save schema version 1, data-driven definitions, and an Undercity-only prototype. Windows PC only is approved for 1.0; distribution channel and minimum supported PC requirements remain open. Save structure is a reversible prototype default, not a production approval. Modular encounter-zone architecture with seamless-looking transitions was approved by the user on 2026-10-24; current palette-only modules and their test boundary remain provisional.
